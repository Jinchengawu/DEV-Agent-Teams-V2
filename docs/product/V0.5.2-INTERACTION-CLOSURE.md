## 1. 产品结论

v0.5.2 不扩张 Agent-Team-OS 的能力边界，而是把已有控制面能力组织成一个无需理解内部架构也能完成的用户闭环：

```text
登录
→ 准备中心
→ 创建可转正式的评测项目
→ 输入交付目标并确认执行边界
→ Plan / Design Gate
→ Workcell 与 AgentAttempt
→ Candidate / Verification
→ Evidence 回读
→ 完成项目引导
```

本阶段在 Apply 前停止。Release Approval、Forward-only Apply、远端 Repository 写入和
Receipt/read-back 继续保持独立授权边界。

### 2.2 Interpretation

1. 产品领域模型与权限边界基本正确，主要缺口已从“有没有控制面能力”转为“用户能否按唯一正确路径完成交付”。
2. 当前交互更适合熟悉架构的开发者，不足以让交付负责人独立判断准备度、阻塞原因和下一动作。
3. Readiness 仅在 Settings 展示会导致用户过晚发现阻塞；它必须成为创建 Delivery 前的产品门禁。
4. 历史迁移项目作为默认入口会混淆评测数据、正式项目和兼容历史。

### 2.3 Assumption

1. v0.5.2 仍是受控本地产品，不以公网多租户或生产 SaaS 为目标。
2. 交付负责人需要理解目标、审批、证据和风险，不需要先理解 Adapter、Provider 或 CAS 实现细节。
3. Deterministic 与真实 Codex 能在同一 Revision 上使用隔离评测数据完成闭环。
4. Knowledge Gate A/B/C 对基础交付是可选项；只有选中明确依赖 Knowledge Context 的 Pipeline 时才阻断。

### 2.4 Accepted Product Decision（已授权本地实施）

1. 版本定位为 `v0.5.2 Interaction Closure`，不并入 v0.6 后移能力。
2. 首要用户为交付负责人；平台管理员和开发者 Agent 是次要用户。
3. Runtime 未就绪时允许编辑目标和查看边界，但禁止启动真实 Delivery。
4. 登录后若系统或项目尚未准备完成，默认进入全局准备中心。
5. 评测项目使用持久化 onboarding 状态，可在同一 Project 内转为正式项目。
6. v0.5.2 必须同时通过同一 Revision 的 Deterministic 与真实 Codex 浏览器闭环。
7. 用户闭环到 Evidence 回读为止，不执行 Apply。

### 2.5 Unknown

1. 真实 Codex 闭环在正式候选环境中的稳定时延和 P95/P99。
2. 真实 Codex 在默认 120 秒单调用预算下能否稳定完成 Planning 与五个 Workcell；300 秒隔离实验不改变该合同。
3. 四仓真实 Live 执行所需权限和当前资格状态。
4. 正式候选是否能形成 `FAIL=0 / WARN=0 / skipped=0` 的 Release Report。

## 3. 用户与核心任务

### 3.1 首要用户：交付负责人

需要完成：

- 判断系统和项目是否具备执行条件；
- 定义交付目标和验收边界；
- 审批计划与设计；
- 观察 Workcell、AgentAttempt、Verification 和恢复状态；
- 在 Candidate 决策前回读可信 Evidence；
- 明确知道何时必须停止并交由管理员处理。

### 3.2 次要用户

## 4. 产品目标与非目标

### 4.1 Must

1. 用户登录后一屏内看到准备状态、阻塞原因和唯一下一动作。
2. 系统与项目 Readiness 使用同一事实源，不由各页面自行推导。
3. 阻塞状态下目标草稿不丢失，但启动动作前后端均 fail-closed。
4. 新评测项目具备可恢复、可审计的 onboarding 状态。
5. 从评测项目创建到 Evidence 回读只需要沿一条主路径操作。
6. Delivery Detail 始终显示当前阶段、已完成阶段、阻塞点、下一动作和所需角色。
7. 业务中文为主，Canonical Identifier、Revision、SHA、CAS 和 Provider 信息按需展开。

### 4.2 Should

1. 用户修复阻塞并刷新后，无需重填目标即可继续。
2. 评测项目完成引导后保留原 Project、Workspace、Delivery 和 Evidence，不复制数据。
3. 桌面和移动端保持相同的状态语义和动作顺序。
4. 智能体页面默认回答“哪些 Deployment 可用”，创建/编辑表单按需打开。

### 4.3 Non-goals

1. 不实现 AgentScope Workcell Live Adapter。
2. 不新增 Evaluation Console。
3. 不扩大 Feishu、Ollama 或 Knowledge Gate A/B/C 的能力范围。
4. 不自动运行 Release Gate、批准 Release 或执行 Apply。
5. 不把 Deterministic 证据表述为真实 Codex 证据。
6. 不进行纯品牌换肤或复制另一产品的视觉样式。

## 6. 核心用户流程

### 6.1 准备中心

准备中心按顺序展示：

1. Runtime：Python、ACWM、AgentScope、Git、Codex CLI、Codex Login、Method Pack。
2. Project Workspace：工作区、Repository、种子 Revision、活动租约。
3. Execution Contract：默认 Pipeline、TeamTemplate、Deployment、Provider Binding。
4. Verification：每仓 Verification Profile 与工具链资格。
5. Optional Knowledge：仅在 Pipeline 依赖时进入阻塞集合。

每项必须显示：稳定 ID、状态、影响范围、中文说明、修复入口和刷新动作。界面不得直接执行需要外部权限的修复。

### 6.2 评测项目

首次使用创建 `guided_evaluation` Project：

- 预选当前已发布且可用的 Pipeline、TeamTemplate 与 Deployment；
- 使用正常 Project、Workspace 和权限模型；
- 不创建独立 Demo 领域实体；
- “历史迁移项目”进入兼容项目分组，不再成为默认主路径。

持久化 onboarding 状态：

```text
setup → in_evaluation → ready
```

- `setup`：Runtime 或项目依赖不完整。
- `in_evaluation`：准备条件已满足并绑定一条评测 Delivery。
- `ready`：评测 Delivery 到达 Candidate 决策点，必要 Verification/Evidence 有效，Administrator 显式确认完成引导。

完成 onboarding 不要求 Apply；同一 Project 直接保留为正式项目。

### 6.3 交付工作台

首屏顺序：

1. 当前项目和准备度；
2. 阻塞原因与唯一下一动作；
3. 交付目标；
4. Pipeline、Workspace、Agent 与 Verification 摘要；
5. 边界预览；
6. 最近运行。

当前宣传 Hero 移入帮助面板。用户可以在 blocked 状态编辑目标并进入“边界预览”，但“确认并启动”保持禁用。

### 6.4 Delivery 运行室

固定阶段时间线：

```text
Boundary → Plan Gate → Design Gate → Workcells → Verification → Candidate → Evidence
```

每个阶段显示：状态、负责身份、输入/输出、证据、失败原因、恢复动作和需要的权限。页面固定一个主动作，不同时竞争展示多个高风险操作。

### 6.5 Evidence 回读与引导完成

评测 Delivery 到达 Candidate 决策点后：

- 展示 Base/Candidate Revision、Diff SHA、Verification、ReviewArtifact 与不可变 Evidence；
- 提供项目 Evidence 深链；
- Administrator 可使用 CAS 与当前 Candidate Gate subject 完成 onboarding；
- 页面明确说明项目已 ready，但 Candidate 尚未 Apply。

## 7. 公共接口契约

### 7.1 Project onboarding

`ProjectCreate` 新增：

```text
onboarding_mode?: "guided_evaluation" | "standard"
```

默认 `standard`。`ProjectDetail` 新增只读 `onboarding` 投影，包含 status、evaluation_delivery_id、version 与时间。

### 7.2 Setup Readiness

新增：

```text
GET /v1/setup-readiness?project_id=<project-id>
```

返回 global、project 和 optional checks；每项至少包含：

- `id`
- `status: ready | blocked | failed | not_run`
- `summary`
- `repair`
- `navigation_target`
- `blocking_scope: start_delivery | complete_onboarding | release_only`

`navigation_target` 只能指向产品内部受控路由，不接受外部任意 URL。

### 7.3 Delivery

`DeliveryCreate` 新增：

```text
purpose?: "product" | "onboarding_evaluation"
```

默认 `product`。服务端在创建前重新检查 Readiness；阻塞时返回 `409 DELIVERY_READINESS_BLOCKED`，并携带同源检查项。

### 7.4 完成 onboarding

新增：

```text
POST /v1/projects/{project_id}/onboarding/complete
```

请求包含 onboarding CAS version、evaluation_delivery_id 与 expected Candidate Gate subject SHA。仅 Administrator 可调用。服务端必须验证项目归属、Delivery 状态、Gate subject 与必要 Evidence。

## 8. 权限与失败处理

| 场景 | 行为 |
|---|---|
| Runtime blocked | 可编辑目标；禁止启动；展示全局修复入口 |
| 项目依赖 blocked | 可查看项目；禁止启动；定位具体 Pipeline/Deployment/Workspace |
| Readiness 在确认期间漂移 | 服务端 409；保留草稿；刷新检查项 |
| Setup Readiness 请求失败 | 状态为 unknown/failed；禁止启动，不能乐观放行 |
| 已有活动 Delivery | 复用/进入当前运行，不创建重复评测 Delivery |
| 评测 Delivery 失败 | onboarding 保持 `in_evaluation`，允许从同一项目恢复或创建明确的新评测运行 |
| CAS 冲突 | 重新读取状态和证据，禁止覆盖新版本 |
| Viewer | 只读查看，不显示确认或创建动作 |

## 9. 验收标准

### 9.1 自动化

1. Migration 为既有项目回填 `ready`，重复执行幂等。
2. 非法 onboarding 跳转、跨项目 Delivery、过期 CAS 和错误 Gate subject 全部拒绝。
3. 前端 disabled 与服务端 409 使用同一 Readiness 事实。
4. 修复并刷新后目标草稿不丢失。
5. 项目切换、刷新恢复、无 Pipeline、无 Deployment、请求失败、长目标和移动端均有测试。
6. Viewer、Editor、Administrator 权限与按钮可见性匹配后端权限。

### 9.2 浏览器闭环

同一 Git Revision 必须分别通过：

1. Deterministic 浏览器闭环；
2. 真实 Codex 浏览器闭环。

两条路径都必须覆盖：新账号登录、准备中心、评测项目、阻塞门禁、目标创建、Plan/Design Gate、Workcell、Verification、Candidate、Evidence 和 onboarding 完成。

### 9.3 正式交接边界

交互闭环通过不等于正式版本发布。正式交接仍要求同 Revision Browser、Deterministic、Live Release Gate 与 `FAIL=0 / WARN=0 / skipped=0`。Apply 仍需独立授权、Receipt 和 read-back。
