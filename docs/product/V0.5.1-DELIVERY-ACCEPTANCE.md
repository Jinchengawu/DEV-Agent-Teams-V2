## 1. 结论

v0.5.1 的版本一致性、Delivery Bundle、Manifest/hash、显式 Product Root、Method Pack
初始化入口和分发架构文档已经实现。主任务没有直接接受委派 Agent 的自报，而是从隔离 wheel
路径构造完整产品 App；首次复核发现 Bundle 漏装 Evaluation Dataset，二次整改后该缺口已关闭，
完整 `build_preview_app()` 可以构造，Console `/` 返回 HTTP 200。

本轮仍**不接受为冻结的 Local Evaluation Delivery Candidate**，原因是：

1. 当前工作树未提交，Builder 正确把 Bundle 标记为 `development_only_dirty_worktree`；
2. 隔离 App 的 `/v1/readiness` 返回 HTTP 503、`not_ready`；
3. 完整 Python suite 在当前沙箱为 `610 passed / 1 skipped / 10 failed / 18 errors`；
4. 没有完成同 Revision 的真实浏览器核心闭环；
5. Deterministic、Live、Release Approval、Apply/read-back 均未运行。

因此，当前成果可交给开发者继续形成 clean Revision 候选，但不能被称为正式可交付版本。

## 3. 首轮审查发现与二次整改

### Finding A：静态 HTTP 200 不能证明完整产品 App 可构造

首轮实现只用 `install_preview_ui()` 验证 Console HTTP 200。主任务从隔离 wheel 调用
`build_preview_app()` 后发现缺少：

`evaluation/datasets/agent-team-os-mvp/1.3.0/manifest.json`

导致 `EvaluationService` 报 `EVALUATION_DATASET_INVALID`。

### Remediation A

委派 Agent 将真实公开 Evaluation Dataset 纳入 allow-list、Manifest、Product Root 校验与敏感路径
扫描，并增加从 Bundle 调用 `load_evaluation_dataset()` 的回归测试。主任务二次 clean-room 复跑后，
完整 App 构造和 Console HTTP 200 通过。

### Residual

该整改只关闭静态 Product Root 依赖遗漏。Runtime Provider readiness、真实登录、核心浏览器旅程与
正式 Gate 仍没有通过。

## 4. 解释

1. 分发机制已经从“隐式依赖源码目录”提升为“显式、可校验、可追溯的 Delivery Bundle”。
2. Bundle 的完整 App 构造证据比单纯静态文件 200 更强，但仍是进程内本地证据，不等同于真实浏览器
   或 Live Agent 证据。
3. dirty development bundle 能验证机制，不能证明某个冻结 Revision 的可复现制品。
4. 当前最主要剩余工作不是增加 Bundle 功能，而是在 clean Revision 和合格 Runtime 上重跑验收阶梯。

## 5. 假设

1. 提交后的目标 Revision 仍将基于本次 `main@b384e83` 及当前工作树变更形成。
2. 现存 `.agent-team-os/live-v051/method-packs` 是已资格化本地快照；主任务只将其复制到临时 Data Dir
   用于 App 构造，没有把它装入 Bundle 或声明为新的资格证据。
3. loopback 与 SQLite extension 失败在具备仓库规定运行时的环境中可以重跑；该假设尚未在本轮验证。

## 9. 下一验收事件

由开发者在正常分支/PR 流程中形成 clean Revision 后，按以下顺序重跑：

1. CI 全量静态、Python、Console、OpenAPI 和 build 检查；
2. 从该 clean Revision 构建正式 Bundle，确认 `source_worktree_clean=true`；
3. 在规定 Python/SQLite Runtime 中完成零失败的 clean-room install/start/readiness/health；
4. 使用独立临时评测账号完成同 Revision 核心浏览器闭环；
5. 再由授权人决定是否进入 Deterministic/Live Release Gate；
6. 只有同 Revision Release Report 达到 `FAIL=0 / WARN=0 / skipped=0`，才可请求正式 Accept；
7. Approval 与 Apply 仍需单独授权和 Receipt/read-back。

本轮没有 commit、push、PR、merge、Gate Approval、Release Approval、Apply 或外部系统写入。
