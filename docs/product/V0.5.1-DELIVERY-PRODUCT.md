## 1. 结论与状态边界

本交付版本的目标不是新增业务功能，而是把当前已经存在的 Agent-Team-OS v0.5.1
能力整理为一个**身份一致、可从干净环境安装、可启动、可评测、可审计交接**的本地交付候选。

本版本同时定义两个不可混淆的完成层级：

| 层级 | 定义 | 本轮是否可完成 |
|---|---|---|
| `Local Evaluation Delivery Candidate` | 从版本化交付包安装，在无源码目录依赖的临时环境中完成启动、健康检查、核心浏览器冒烟与证据索引 | 是，本轮实施目标 |
| `Formal Live Accepted` | 同一 Git Revision 的核心浏览器、Deterministic Gate、Live Gate 与 Release Report 均满足 `FAIL=0 / WARN=0 / skipped=0`，并完成授权要求 | 否，需要外部凭据、四仓状态与独立授权 |

任何本地测试、构建、交付包或浏览器冒烟通过，都不得自动提升为 `Formal Live Accepted`、
Release Approved 或 Applied。

## 2. 证据分类

### 2.1 Fact

1. `main` 与 `origin/main` 当前均指向 `b384e83b701d58ffaaf97c2cad0bf8958387784c`。
2. UI/UX 二次整改已经合入该 Revision；它只证明相应 UI 整改进入 `main`，不证明完整产品发布。
3. `pyproject.toml`、`console/package.json` 与控制台 Shell 仍显示 `0.5.0`，而产品总纲声明当前开发目标为 `0.5.1`。
4. 当前 Preview Runtime 通过仓库根目录查找 `migrations/`、`config/` 与 `console/dist/`；Python wheel 仅声明打包 `src/agent_team_os`。
5. 仓库已经提供 Delivery Handoff Evidence 检查器；该检查器只引用和校验证据，不产生 Gate 成功，也不执行 Apply。
6. 仓库规则要求主要版本在同一 Git Revision 上通过核心浏览器、Deterministic 与 Live Release Gate，且 Release Report 必须为 `FAIL=0 / WARN=0 / skipped=0`。

### 2.2 Interpretation

1. 当前代码可以作为源码工作区中的本地构建候选，但还不能被称为可独立交接的产品交付物。
2. 最小正确修复不是宣称 Live 已完成，而是建立一个显式的 Delivery Bundle，使运行所需资源、版本身份和证据清单可验证。
3. Delivery Bundle 应复用现有 Release/Handoff 事实源，不应新增另一套 Gate 或 Apply 权威。

### 2.3 Assumption

1. 首个交付对象是受信任的本地评测人员或开发者，而不是公网生产用户。
2. 交付环境满足 Python `>=3.11,<3.13`，且能够使用仓库规定的前端构建工具生成静态资源。
3. 本轮允许改变本地分发与资源定位方式，但不改变 ACWM、Agent-Team-OS、AgentScope、Hermes 或 Codex 的权威边界。

### 2.4 Decision

1. 采用“版本化 Delivery Bundle + 显式 Product Root”作为 v0.5.1 本地交付策略。
2. Bundle 的目标是脱离源码 checkout 运行，而不是把所有外部 Live Provider 或四仓数据嵌入产物。
3. 本轮不执行 Gate 审批、Release Approval、Apply、外部仓库写入、凭据刷新、部署或发布。
4. 本轮实施完成后由主任务独立审查；开发 Agent 的自报结果不能单独构成验收。

### 2.5 Unknown

1. 正式 Live 环境中的 Feishu、Ollama、Codex、Hermes、GitHub 权限和可用性。
2. 四仓 Verification Profile 在当前工具与依赖身份下能否重新资格化。
3. Live Planning 超时的工程原因与正式超时策略。
4. 当前 Revision 是否能够形成 `FAIL=0 / WARN=0 / skipped=0` 的完整 Live Release Report。
5. 最终对外分发渠道、签名策略与长期升级/回滚服务等级；这些属于后续产品决策。

## 3. 产品定位与目标用户

Agent-Team-OS 是交付控制面，不是多 Agent 聊天界面。它让评测者和交付负责人看见并约束：

- Project、TeamTemplate、Pipeline 与不可变 Snapshot；
- 产品可观察的 Workcell Composition、AgentAttempt 与生命周期；
- Candidate、Verification、Approval、ReleaseBundle、Apply 与 Receipt；
- Evidence、Knowledge、权限、Workspace 隔离与恢复状态。

本交付版本面向三类用户：

| 用户 | 核心任务 | 交付版本必须提供 |
|---|---|---|
| 本地评测者 | 在不依赖开发者工作区的环境中启动并检查产品 | 明确安装入口、临时评测账号、健康检查与浏览器路径 |
| 开发者 Agent | 复现、定位并修复候选问题 | 版本身份、Manifest、确定性检查和失败原因 |
| 发布/验收负责人 | 判断候选是否具备进入正式 Gate 的条件 | 同 Revision 证据索引、未运行项和授权边界 |

## 4. 用户问题

当前本地 Alpha 已有较完整控制面能力，但交接仍存在四个结构性问题：

1. **身份漂移**：产品文档目标、Python 包、Console 包与 UI 展示版本不一致。
2. **运行根依赖**：安装后的 Runtime 隐式假设源码仓库布局存在，无法证明干净环境可运行。
3. **交付物不完整**：代码包与 Console、Migration、配置资源没有形成单一可校验交付单元。
4. **证据易被夸大**：本地测试、Deterministic、Live、Release Approval 与 Apply 缺少交付层面的清晰分隔。

## 5. 版本目标与非目标

### 5.1 Must

1. 所有用户可见和制品可见版本身份统一为 `0.5.1`。
2. 能生成带 Manifest 和哈希的版本化 Delivery Bundle。
3. Bundle 包含本地启动所必需的后端安装物、Console 静态产物、Migration 与锁定配置资源。
4. Runtime 支持经校验的显式 Product Root，并保留源码 checkout 启动兼容性。
5. 在独立临时目录中验证 Bundle 内容、安装、数据库初始化、启动、健康检查与 UI 静态资源。
6. 交接文档记录 Git SHA、制品哈希、实际命令、通过/失败/跳过项与证据范围。
7. 独立评测账号在交接时生成；密码不得进入 Git、日志、Fixture、Gate Report、截图或提交文档。

### 5.2 Should

1. 构建失败应指明缺少的构建前置条件或资源，而不是静默产生残缺 Bundle。
2. Manifest 应使用稳定排序和相对路径，便于重复构建比较。
3. 交付包检查应复用 CI 和现有 Handoff Evidence 规则。

### 5.3 Later

1. 制品签名、远程 Registry、自动升级与回滚服务。
2. 容器镜像或多平台安装器。
3. 正式生产部署编排。
4. AgentScope Workcell Live Adapter。

### 5.4 Non-goals

1. 不复制 ACWM Runtime Contract，不引入第二套 Gate/Loop/Artifact Contract。
2. 不创建产品不可见的 Hidden Child。
3. 不改变 Apply、Forward-only Release 或补偿语义。
4. 不写入 Feishu、GitHub 或四个业务仓库。
5. 不批准 Gate，不执行 Apply，不创建或合并 PR，不推送远程分支。
6. 不把 Deterministic Adapter 描述为 Live Agent 证据。

## 6. 核心用户旅程

### 6.1 构建交付候选

1. 构建者在已对齐的 `main` Revision 上运行 Console build、Python build 与 Delivery Bundle builder。
2. Builder 对必要资源做存在性和安全检查。
3. Builder 输出版本化目录或归档、Manifest、文件哈希和产品 Git SHA。
4. 缺少资源、版本不一致或发现不允许内容时，构建 fail-closed。

### 6.2 干净环境评测

1. 评测者将 Bundle 解压到临时目录。
2. 从 Bundle 中安装后端制品，并通过 Bundle 指定的 Product Root 启动。
3. 使用独立临时数据库和运行目录初始化本地系统。
4. 由受控步骤生成一次性评测账号，凭据只在交接通道中提供。
5. 检查 readiness、health、登录和核心浏览器路径。
6. 停止服务并保留不含凭据的报告和 Manifest。

### 6.3 正式验收衔接

1. 本地候选通过后，验收负责人取得同 Revision 的 Browser、Deterministic 与 Live 报告。
2. Handoff Evidence 检查器只检查引用一致性与报告结果。
3. 任一报告存在 `FAIL`、`WARN`、`skipped`、Revision 不一致或缺失，则正式验收保持 blocked。
4. Approval 与 Apply 由已授权主体另行决策和执行。

## 7. 功能需求

### FR-1 统一版本身份

- Python metadata、Console metadata、产品 UI 和交付 Manifest 必须报告 `0.5.1`。
- 自动检查发现版本不一致时必须失败。

### FR-2 Delivery Bundle Builder

- 输入：已构建的 Console、Python 制品、锁定配置、Migration、当前 Git Revision。
- 输出：版本化 Bundle 与机器可读 Manifest。
- Manifest 至少记录 schema、product version、Git SHA、生成时间、文件路径、大小和 SHA-256。
- Builder 不得收集运行数据库、日志、缓存、密钥、Token 或用户工作区内容。

### FR-3 Product Root 解析

- 支持显式配置 Bundle Product Root。
- Root 必须存在且包含要求的资源；不合法时 fail-closed。
- 未显式配置时，源码 checkout 的现有开发启动方式继续可用。
- Product Root 不得改变 Workspace、Repository 或 AgentAttempt 的权限边界。

### FR-4 干净环境验证

- 验证必须从 Bundle 副本运行，而非回落读取原源码目录。
- 至少覆盖资源完整性、安装、Migration、readiness/health 和 Console 入口。
- 验证报告必须显示未运行的 Browser、Deterministic、Live、Approval 和 Apply 状态。

### FR-5 证据与交接

- 复用现有 Delivery Handoff Evidence，不创建另一个 Release 判定器。
- 所有证据必须绑定 Revision；不一致时不得汇总为通过。
- 报告必须把 `local`、`deterministic`、`live`、`release approval`、`apply/read-back` 分栏展示。

## 8. 非功能与安全要求

1. **Fail-closed**：缺失资源、版本冲突、Manifest 哈希错误或非法 Product Root 必须阻止启动或构建。
2. **可重复**：除生成时间等声明字段外，Manifest 内容顺序稳定，文件哈希可重复校验。
3. **最小权限**：Bundle 不携带外部凭据，不扩大 Workspace 或 Repository 权限。
4. **可追溯**：每个交付候选可追溯到唯一 Git SHA 和制品哈希。
5. **兼容性**：继续支持 Python `>=3.11,<3.13`；源码开发启动不被破坏。
6. **可恢复**：验证使用隔离临时状态，不修改操作者现有数据库和运行数据。
7. **中文优先**：交付说明和错误指引使用简体中文，Canonical Identifier 保留英文。

## 9. 交付切片与验收标准

| ID | 用户价值 | 可观察验收 | 证据 |
|---|---|---|---|
| DLV-001 | 识别正在评测的真实版本 | 所有受控版本入口均为 `0.5.1`，一致性测试通过 | diff + version check |
| DLV-002 | 获得完整交付物 | Builder 生成 Bundle 和 Manifest，缺资源时失败 | focused tests + sample manifest |
| DLV-003 | 脱离源码目录运行 | 临时目录安装并读取 Bundle 资源，无源码 fallback | clean-room smoke |
| DLV-004 | 安全交接 | Bundle/报告不含凭据和运行数据；评测账号独立生成 | deny-list test + runbook review |
| DLV-005 | 证据不越界 | 报告明确显示 Local 与 Gate/Apply 状态 | handoff check + document review |
| DLV-006 | 可进入主任务验收 | CI 对齐检查和本地浏览器冒烟均有实际结果 | command ledger + browser receipt |

## 10. 发布判定矩阵

| 证据 | Local Candidate | Formal Live Accepted |
|---|---:|---:|
| 版本一致性 | 必须通过 | 必须通过 |
| Bundle 完整性与哈希 | 必须通过 | 必须通过 |
| 干净环境安装/启动 | 必须通过 | 必须通过 |
| 核心浏览器冒烟 | 必须，同 Revision | 必须，同 Revision、零容差 |
| Deterministic Gate | 可记录为未运行，不得冒充通过 | 必须 `FAIL=0/WARN=0/skipped=0` |
| Live Gate | 可记录为 blocked/not run | 必须 `FAIL=0/WARN=0/skipped=0` |
| Release Approval | 不执行 | 需要授权主体明确批准 |
| Apply 与 read-back | 不执行 | 需要单独授权且必须有 Receipt/read-back |

## 11. 可观测性与报告

交付候选的报告至少包含：

- product version 与 Git SHA；
- Bundle 路径、归档哈希、Manifest schema；
- 构建和验证命令的 exit status；
- 安装、Migration、health、readiness、Console、浏览器结果；
- Deterministic、Live、Approval、Apply 的明确状态；
- 已知失败、跳过、环境限制和证据路径；
- 当前 Git 状态以及是否 commit/push/PR/merge（必须以观测事实为准）。

## 12. 退出条件

### 12.1 本轮成功

只有同时满足以下条件，主任务才可将本轮标记为 `locally_verified`：

1. DLV-001 至 DLV-005 实现并由自动测试覆盖；
2. 从隔离目录完成 Bundle 安装与启动验证；
3. 核心浏览器路径在相同 Revision 上有新证据；
4. 主任务复查最终 diff、失败路径和证据边界；
5. 文档与架构状态完成 reconciliation；
6. 所有未运行项被明确记录，没有被转换为“通过”。

### 12.2 正式发布仍保持 blocked 的条件

只要以下任一项成立，就不得称为正式交付完成：

- Live Provider 或四仓权限未验证；
- Browser、Deterministic、Live 不是同一 Revision；
- Release Report 不是 `FAIL=0 / WARN=0 / skipped=0`；
- Approval、Apply 或 read-back 没有授权与 Receipt；
- 独立评测账号和交接证据未提供。

## 13. 后续决策
